# ADR 008 — Local accounts and owner-scoped persistence

October 21, 2026. Existing stack has no auth/database. Select Better Auth 1.7.12 for established password/session implementation and better-sqlite3 13.0.3 for durable local storage. No custom password cryptography, paid service or public deployment. Official references: https://better-auth.com/docs/installation ; https://better-auth.com/docs/concepts/database ; https://better-auth.com/docs/concepts/session-management ; https://better-auth.com/docs/concepts/rate-limit ; https://sqlite.org/whentouse.html . Better Auth supports SQLite and PostgreSQL; SQLite avoids a server for the current single-host milestone. Future multi-instance deployments require a managed backup/concurrency plan and likely PostgreSQL adapter, not database credentials in mobile clients.

Domain types/validation, application repository contracts, infrastructure SQLite/auth adapters, and API/UI composition remain separate. All user-data SQL predicates include authenticated owner ID. Owner IDs are never accepted from request bodies. Foreign keys, unique owner/source pins and owner-coordinate custom pins, transactional migrations, UUID IDs, private defaults and audit timestamps enforce persistence constraints. Sharing eligibility is separate from visibility: pins remain PRIVATE and no public endpoint or publishing exists. Preferences contain owner-validated favorites, regions/species, units, IANA zone, opt-in, lead time and quiet hours; no notification delivery.

Better Auth controls credential hashes and cookie signatures. Only registration/login/logout/session routes exposed; success JSON is sanitized to exclude tokens. HttpOnly SameSite cookies, Secure on HTTPS, server-side session lookup without cookie-cache authorization, expiration and logout revocation. Mutation requests require exact configured Origin and JSON. Explicit local base URL; no wildcard origins. Auth rate limiter enabled with database persistence; current direct local server uses a fixed bucket rather than trusting spoofable client IP headers. This is conservative single-host behavior, not a scalable production abuse policy.

Init command creates an untracked private data directory and random secret (0600) only if absent; never prints secret. SQLite database persists on disk with schema migration tracking. Auth migrations use the library's official migration API; application migrations are versioned SQL. Build/ordinary public routes need not open private storage. Missing setup returns a generic service-unavailable error. No user data/coordinates/credentials logged. Database is not encrypted at rest; filesystem security/backups and protected hosting remain production prerequisites.

Registration is local email/password without verified email ownership. No email transport is configured, so recovery and email verification are explicitly unavailable, not simulated or logged reset links. No real PII in tests. This limits production readiness; it does not block testing local register/login/save/edit/logout/login flows.
